1. EXECUTIVE SUMMARY
================================================================================

This is a professional, production-ready backend API for an Egyptian Museum 
management system.

WHAT IT DOES:
✓ User authentication (register, login, profile management)
✓ Browse and scan ancient artifacts
✓ Find shortest paths between rooms (Dijkstra's algorithm)
✓ Create and manage guided tours
✓ AI chat about artifacts
✓ Feedback and rating system
✓ Multi-language support (English & Arabic)

SECURITY:
✓ JWT authentication
✓ Password hashing
✓ Input validation
✓ SQL injection prevention
✓ CORS enabled

3. DATABASE SCHEMA
================================================================================

USERS TABLE:
- Id (Primary Key)
- Email (Unique)
- Password (Hashed)
- UserName
- Name (Display Name - Can be changed)
- PreferredLanguage (en/ar)
- CreatedAt
- IsDeleted

MAPS TABLE:
- Id (Primary Key)
- Name
- Zone
- ImageUrl
- CreatedAt
- IsDeleted

ROOMS TABLE:
- Id (Primary Key)
- Name
- Description
- MapId (Foreign Key)
- XCoord (X Coordinate)
- YCoord (Y Coordinate)
- CreatedAt
- IsDeleted

INDOOR_MAP_PATHS TABLE (Graph Edges):
- Id (Primary Key)
- MapId (Foreign Key)
- FromRoomId (Foreign Key)
- ToRoomId (Foreign Key)
- CreatedAt
- IsDeleted
NOTE: Distance calculated from coordinates, NOT stored

PIECES TABLE (Artifacts):
- Id (Primary Key)
- Code (Unique Barcode)
- Name
- PhotoPath
- RoomId (Foreign Key)
- CreatedAt
- IsDeleted
- Translations (English/Arabic)

TOURS TABLE:
- Id (Primary Key)
- Name
- Description
- DurationMinutes
- Category
- CreatedAt
- IsDeleted

TOUR_ROOMS (Junction Table):
- TourId (Foreign Key)
- RoomId (Foreign Key)
- Order
- Primary Key: (TourId, RoomId)

CHAT_CONVERSATIONS TABLE:
- Id (Primary Key)
- UserId (Foreign Key)
- Type (General/Artifact)
- Title
- ArtifactId (Foreign Key, nullable)
- CreatedAt
- IsDeleted

CHAT_MESSAGES TABLE:
- Id (Primary Key)
- ConversationId (Foreign Key)
- SenderType (User/AI)
- Message
- CreatedAt

FEEDBACK TABLE:
- Id (Primary Key)
- UserId (Foreign Key)
- TargetType (App/Artifact/Chat)
- TargetId
- Rating (1-5)
- Comment
- CreatedAt
- IsDeleted

5. AUTHENTICATION & SECURITY
================================================================================

JWT TOKEN FLOW:

1. User sends email + password to POST /auth/login
2. Server validates credentials
3. Server creates JWT token
4. Server sends token back to user
5. User stores token in app/browser
6. User includes token in Authorization header: "Bearer TOKEN"
7. Server validates token on every request
8. If valid: Access granted ✓
9. If invalid/expired: 401 Unauthorized

HOW TO USE TOKEN:

Header Format:
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

cURL Example:
curl -X GET http://localhost:5000/api/auth/me \
  -H "Authorization: Bearer YOUR_JWT_TOKEN"

Postman:
1. Get token from login response
2. Go to Headers tab
3. Add: Key = "Authorization", Value = "Bearer YOUR_TOKEN"

TOKEN EXPIRATION:
- Default: 60 minutes
- Configurable in appsettings.json
- After expiration: Must login again

SECURITY FEATURES:

✓ Password Hashing: PBKDF2 (ASP.NET Identity)
  - Passwords never stored as plain text
  - Random salt for each password
  - 10,000+ iterations for hashing

✓ JWT Validation:
  - Algorithm: HS256 (HMAC with SHA-256)
  - Issuer: MuseWay
  - Audience: MuseWayApp
  - Contains: User ID, Email, Name, Subject

✓ Input Validation:
  - Null checks
  - Length validation
  - Format validation
  - Type checking
  - Range validation

✓ SQL Injection Prevention:
  - Using Entity Framework Core ORM
  - Parameterized queries
  - No raw SQL strings

✓ CORS:
  - Cross-Origin Resource Sharing enabled
  - Can be called from any origin
  - Configurable in Program.cs

✓ Error Handling:
  - Safe error messages
  - Don't expose database structure
  - Stack traces hidden in production
  - Logging all errors

6. ERROR HANDLING & STATUS CODES
================================================================================

HTTP STATUS CODES:

200 OK
- Successful GET request
- Request processed successfully
- Data returned

201 CREATED
- Resource created successfully
- New ID returned
- Location header included

400 BAD REQUEST
- Invalid request format
- Missing required fields
- Invalid field values
- Validation failed
Example Response:
{
  "success": false,
  "message": "Display name must be between 3 and 100 characters"
}

401 UNAUTHORIZED
- Missing JWT token
- Invalid JWT token
- Expired JWT token
- User not authenticated
Example Response:
{
  "success": false,
  "message": "Unauthorized"
}

403 FORBIDDEN
- User authenticated but not authorized
- Doesn't have permission
- Not your resource

404 NOT FOUND
- Resource doesn't exist
- Invalid ID
- Wrong URL
Example Response:
{
  "success": false,
  "message": "Room with ID 999 not found"
}

409 CONFLICT
- Business logic violation
- Invalid state transition
- Conflicting data
Example Response:
{
  "success": false,
  "message": "No path exists between room 1 and room 7"
}

500 INTERNAL SERVER ERROR
- Unexpected server error
- Database connection failure
- Code exception
- Try again later

COMMON ERROR MESSAGES:

"Display name cannot be empty"
→ Solution: Provide non-empty display name

"Display name must be between 3 and 100 characters"
→ Solution: Enter 3-100 character name

"Username is already taken"
→ Solution: Choose different username

"User not found"
→ Solution: Check user ID

"Room with ID X not found"
→ Solution: Verify room ID exists

"No path exists between room X and room Y"
→ Solution: Rooms may not be connected

"User not authenticated"
→ Solution: Login and get JWT token

"Room not found with Code: X"
→ Solution: Verify artifact barcode

8. QUERY PARAMETERS & FILTERS
================================================================================

PAGINATION (Artifacts):

GET /api/pieces?page=1&pageSize=12&lang=en

Parameters:
- page: Which page (default: 1)
- pageSize: Items per page (default: 12)
- lang: Language (en or ar)

Example:
- page=1, pageSize=12 → Items 1-12
- page=2, pageSize=12 → Items 13-24
- page=3, pageSize=20 → Items 41-60

LANGUAGE SELECTION:

Query parameter: lang=en or lang=ar

Applied to:
- GET /api/pieces/
- GET /api/pieces/{id}
- GET /api/pieces/GetByCode/{code}

Example:
GET /api/pieces?lang=ar → Returns Arabic descriptions
GET /api/pieces?lang=en → Returns English descriptions

TOUR RECOMMENDATIONS:

GET /api/tours/recommend?category=History&durationMinutes=60&numberOfRooms=5

Parameters (all optional, but at least one required):
- category: Tour type (e.g., "History", "Art")
- durationMinutes: Maximum duration in minutes
- numberOfRooms: Number of rooms in tour

Examples:
- ?category=History → All history tours
- ?durationMinutes=90 → Tours 90 minutes or less
- ?numberOfRooms=5 → Tours with 5 or fewer rooms
- ?category=Art&durationMinutes=120 → Art tours under 2 hours

13. KEY ARCHITECTURAL PRINCIPLES
================================================================================

CLEAN ARCHITECTURE:

Each layer is independent and can be tested separately:

1. DOMAIN LAYER
   - Contains business entities
   - No external dependencies
   - Defines what data exists
   - Example: Room.cs, User.cs

2. APPLICATION LAYER
   - Business logic & orchestration
   - Service interfaces & implementations
   - DTOs (Data Transfer Objects)
   - No direct database access
   - Example: NavigationService.cs

3. INFRASTRUCTURE LAYER
   - Database access (Entity Framework)
   - Repository implementations
   - Migrations & schema
   - External service integrations
   - Example: NavigationRepository.cs

4. API LAYER
   - HTTP controllers
   - Request/response handling
   - Authentication enforcement
   - Error handling & mapping
   - Example: NavigationController.cs

BENEFITS:

✓ Testability: Each layer testable independently
✓ Maintainability: Changes isolated to specific layers
✓ Reusability: Services used by multiple controllers
✓ Scalability: Easy to add new features
✓ Professional: Industry-standard approach

DESIGN PATTERNS USED:

1. REPOSITORY PATTERN
   - Abstracts database access
   - Single source of data queries
   - Easy to swap implementations
   - Supports unit testing

2. SERVICE PATTERN
   - Encapsulates business logic
   - Called by controllers
   - Single responsibility principle
   - Reusable across controllers

3. DEPENDENCY INJECTION
   - Loosely coupled components
   - Easy to mock/test
   - Configured in Program.cs
   - Lifetime management

4. DTO PATTERN
   - Separates entities from API
   - Hides internal structure
   - Flexible serialization
   - API versioning support

5. DIJKSTRA'S ALGORITHM
   - Finds shortest paths
   - O(V²) time complexity
   - Graph-based implementation
   - Bidirectional edges
